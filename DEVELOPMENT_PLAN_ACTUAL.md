# Актуальный план развития My Heroes Clicker

Актуально на 2026-05-09.

## Текущее состояние

Проект уже прошел часть исходного плана:

- решение разнесено на `API`, `Browser`, `Core`, `DataSQLite`, `DbMigrator` и `Web`;
- есть SQLite-схема для аккаунтов, активного аккаунта, настроек, сетов и пресетов приемов;
- есть мигратор и запуск backend через предварительное применение миграций;
- есть API CRUD для аккаунтов, настроек, сетов и пресетов приемов;
- есть сценарный каталог, диспетчер занятости вкладок и менеджер сценарных вкладок;
- фарм драки и фарм приключений уже разделены на разные сценарии и разные типы вкладок;
- обработка `/capcha` уже ставит сценарий на паузу и ждет ручного продолжения;
- есть базовый UI запуска фарма, подготовки фарм/боевого режима, остановки и продолжения.

Исходный план нужно считать устаревшим в части "добавить SQLite", "ввести вкладки", "добавить диспетчер", "добавить API для конфигурации" и "проверить базовые маршруты фарма". Эти пункты больше не являются отдельными этапами, но требуют доводки.

## Ближайший фокус

Главная цель следующего прохода - превратить уже собранный каркас в управляемое приложение: UI должен покрывать существующий backend, статусы должны быть понятными, а чувствительные данные и диагностика должны храниться предсказуемо.

## Этап 1. Довести текущий фарм до надежного состояния

- Проверить вживую оба сценария:
  - драка: `/battle1`, fallback `/batle1`, лог `/battle1/log/*` или `/batle1/log/*`;
  - приключения: `/domp1`, атака, лог `/domp1/log/*`.
- Уточнить поведение приключений: если нужен приоритет `/domp1/attack10` и fallback `/domp1/attack`, добавить это явно в `AttackStep`/локаторы.
- Расширить статус сценариев:
  - показывать активный сценарий;
  - показывать имя вкладки;
  - показывать причину паузы;
  - добавить время постановки на паузу;
  - показывать последнее пользовательское событие.
- Разделить `Stop` и `Resume` в UI поведенчески и визуально:
  - `Resume` только снимает паузу;
  - `Stop` отменяет активные сценарии;
  - при captcha после `Resume` сценарий продолжает работу с текущего места.
- Уточнить параллельность фарма:
  - backend уже блокирует конфликтующие сценарии по типу вкладки;
  - UI пока запрещает запуск второго сценария через общий `isRunning`;
  - перед включением параллельного запуска нужно добавить статус по каждому сценарию/вкладке.

## Этап 2. Подключить UI к существующей SQLite-конфигурации

- Добавить страницу или раздел "Настройки".
- Подключить UI к существующим API:
  - `api/accounts`;
  - `api/settings`;
  - `api/equipment-sets`;
  - `api/technique-presets`.
- Реализовать управление аккаунтами:
  - список аккаунтов;
  - создание и редактирование;
  - выбор активного аккаунта;
  - отображение активного аккаунта в шапке вместо "Не выбран".
- Реализовать управление настройками:
  - `baseUrl`;
  - headless-режим;
  - путь профиля браузера;
  - задержки;
  - пороги здоровья;
  - retry-настройки.
- Реализовать управление сетами:
  - список farm/combat сетов;
  - просмотр слотов;
  - ручная правка сохраненных слотов;
  - отдельным шагом добавить "считать текущие вещи" из браузера.
- Реализовать управление приемами:
  - пресеты farm/combat;
  - слоты 1..15;
  - включение/выключение приема;
  - ручная правка названий.

## Этап 3. Безопасное хранение аккаунта

- Зафиксировать правило: пароль не хранится в SQLite открытым текстом.
- Ввести сервис защиты секретов на ASP.NET Core Data Protection:
  - при сохранении аккаунта шифровать пароль;
  - при авторизации расшифровывать пароль только в памяти;
  - в API-ответах не возвращать пароль или возвращать только признак наличия секрета.
- Обновить контракты аккаунта:
  - заменить публичный `EncryptedPassword` на безопасную модель запроса/ответа;
  - не отдавать зашифрованное значение во фронт без необходимости.
- Определить роль `auth_state_path`:
  - основной путь - использовать сохраненное состояние браузера;
  - пароль нужен для первичного входа или восстановления сессии.

## Этап 4. Тревоги, события и диагностика

- Реализовать `WebAlertService` не как заглушку, а как поток событий для фронта.
- Добавить фронтовые звуки:
  - captcha;
  - потеря авторизации;
  - фатальная ошибка сценария;
  - долгий простой или ожидание ресурсов.
- Добавить настройки звука:
  - включено/выключено;
  - громкость;
  - тестовый сигнал.
- Разделить пользовательские события и техническую диагностику:
  - пользовательские события - в UI;
  - технические ошибки - в backend-лог;
  - HTML, URL, screenshot и причина падения - в `failures`;
  - позже добавить Playwright trace при сложных падениях.
- Настроить файловые NLog-targets:
  - пользовательский лог;
  - backend-лог;
  - отдельный каталог crash/dump.

## Этап 5. Сценарный runtime и параллельные сценарии

- Перейти от глобального статуса к статусу по сценариям или вкладкам.
- Для каждого сценария хранить:
  - идентификатор запуска;
  - имя сценария;
  - вкладку;
  - состояние `running/paused/stopping/stopped/failed`;
  - прогресс;
  - последнюю ошибку.
- Разрешить параллельный запуск только там, где нет конфликта по вкладке и ресурсам.
- Для UI добавить отдельные карточки активных сценариев.
- Оставить общий `Stop all`, но добавить точечную остановку сценария.
- Проверить, не конфликтуют ли фарм драки и фарм приключений по состоянию персонажа, здоровью, рвению, сетам и приемам. Если конфликтуют - оставить взаимное исключение на уровне бизнес-правил, а не только вкладок.

## Этап 6. Войны и осады

- Добавить настройки блока "Войны":
  - включено/выключено;
  - период проверки;
  - последняя проверка;
  - последний результат;
  - приоритет относительно фарма.
- Добавить настройки блока "Осады":
  - включено/выключено;
  - период проверки;
  - защита от повторного входа;
  - последний результат.
- Реализовывать через прямые HTTP-запросы там, где достаточно cookie и перехода.
- Использовать Playwright только если вход требует клиентского действия.
- Перед реализацией зафиксировать правило прерывания:
  - война/осада может поставить фарм на паузу;
  - после входа приложение возвращается к фарму, если сценарий не был остановлен вручную.

- Улучшить локальный запуск:

  - dev-режим оставить с видимыми окнами;
  - проверка занятых портов;

- Подготовить формат лаунчера:
  - сначала маленький .NET launcher;
  - Electron/Tauri рассматривать только если понадобится полноценная оболочка.
- Настроить GitHub Actions:
  - `dotnet build`;
  - frontend `npm run build`;
  - frontend `npm run lint`;
  - упаковка артефактов.
- Добавить версионирование и GitHub Releases.
- Подготовить установку:
  - каталог данных пользователя;
  - сохранение SQLite между обновлениями;
  - ярлык;
  - миграции при старте.

## Решения вместо старых открытых вопросов

- Несколько аккаунтов: хранить несколько аккаунтов, одновременно активен один. Параллельный запуск нескольких аккаунтов не входит в ближайший план.
- Captcha: после ручного решения и нажатия "Продолжить" сценарий должен продолжаться автоматически.
- Фарм драки и приключений: технически готовить к параллельной модели, но включать ее в UI только после появления статусов по вкладкам и проверки игровых конфликтов.
- Секреты аккаунта: использовать ASP.NET Core Data Protection поверх SQLite. В SQLite хранить только защищенное значение, во фронт пароль не возвращать.
- Войны и осады: приоритет выше фарма; фарм ставится на паузу, затем возобновляется, если пользователь не остановил его вручную.

## Рекомендуемый порядок работ

1. Статусы по сценариям, улучшенная пауза и корректный UI для активных запусков.
2. UI для существующей SQLite-конфигурации.
3. DPAPI для пароля и безопасные контракты аккаунтов.
4. События, звуки, пользовательский лог и файловая диагностика.
5. Проверенная параллельность или явное бизнес-ограничение фарма.
6. Войны и осады.
7. Лаунчер, CI, релизы и установщик.
